# Cursor Auto Mode Refactor Plan (2026-04-22)

## 目标

这份计划不是为了“找最大最酷的重构”，而是为了筛出**适合低模型能力自动模式**执行的任务。

前提假设：

- 自动模式可持续执行，但模型能力更接近“可靠码农”而不是“架构师 + 审核者 + 研究员”。
- 它更适合做明确、局部、可验证、低歧义的工作。
- 它不适合在同一轮里同时承担：
  - 架构设计
  - 复杂跨模块重构
  - 行为回归审查
  - 隐含需求推理

因此，本计划采用：

- 先分级筛任务
- 再拆成小步
- 每步都附带验收方式
- 对高风险任务强制加人工审核门

## 任务分级规则

### A 类：适合直接交给自动模式

满足以下条件的大多可以直接做：

- 单个任务只涉及 1 到 3 个文件
- 目标是“搬运、抽取、去重、补测试、统一命名、拆常量”
- 行为应该保持不变
- 可以通过 `vitest`、`tsc`、`npm run build` 或肉眼 diff 快速验收
- 失败代价低，回滚简单

典型例子：

- 抽取纯函数
- 拆配置常量
- 去掉重复类型定义
- 把一个大组件里的静态配置提到独立文件
- 给现有纯逻辑补单测

### B 类：可交给自动模式，但必须加人工审核

满足以下特征时，可以让自动模式做“施工”，但不能让它独立闭环：

- 涉及 3 到 8 个文件
- 会改动数据流、状态流、IPC、网关路由、provider 选择
- 看起来是重构，实际上容易引入行为变化
- 测试覆盖不足，无法完全靠自动验证兜底

这类任务必须采用：

1. 人先定义边界
2. 自动模式只做一个子步骤
3. 每步完成后人工 review 再放行下一步

### C 类：不适合直接交给自动模式

以下任务不建议直接放给低配自动模式：

- 需要先做架构判断再写代码的大重构
- 跨 Electron / Frontend / Gateway 的联动式改造
- 涉及隐式协议、历史兼容、灰度切换的任务
- 需要“先读懂系统再决定怎么改”的任务
- 需要它自己判断“这是不是行为回归”的任务

这类任务更适合：

- 先由人写设计
- 再把设计拆成 A/B 类施工单

## 推荐审核机制

低配自动模式不要直接给“自由发挥式重构”，建议统一采用下面的审核门。

### 审核门 1：任务准入

先问四个问题：

1. 这一步是不是局部任务？
2. 这一步是否允许行为零变化？
3. 这一步是否有明确完成标准？
4. 这一步失败后是否容易回滚？

四个问题里只要有两个答不上来，就不要直接交给自动模式。

### 审核门 2：施工约束

给自动模式的提示词里必须写清：

- 只改哪些文件
- 不允许顺手改哪些文件
- 本步是否允许行为变化
- 必须运行哪些验证
- 最终输出要列出风险点

### 审核门 3：人工复核

每个子任务完成后，人至少检查：

- diff 是否超出边界
- 命名是否开始漂移
- 是否把“重构”做成了“逻辑重写”
- 是否新增了没有必要的抽象层
- 测试是否真的覆盖了改动点

## 本项目的重构候选池

下面按“是否适合低配自动模式”排序。

### 优先做：A 类 / A-B 边界任务

#### 1. Provider/Settings 元数据收口

涉及文件：

- `src/hooks/settings/useApiKeys.ts`
- `src/ui/settings/tabs/ConnectionTabView.tsx`
- `src/ui/settings/tabs/ConnectionTabView.Beginner.tsx`
- `src/hooks/settings/recommendedModels.ts`

适合原因：

- 这是前端配置层，边界相对清楚
- 很多内容属于 provider 元数据、推荐模型、错误提示映射
- 可以做“纯搬运 + 去重”，不一定动业务流

推荐拆法：

1. 先统一 provider 类型定义
2. 再统一 provider 元数据来源
3. 再把 beginner / advanced 共用逻辑抽成 helper
4. 最后补 provider utils 测试

审核要求：

- 每一步都要保证设置面板可编译
- 不允许同时改 Electron 保存逻辑

#### 2. 纯工具函数补测试

候选文件：

- `src/utils/providerUtils.ts`
- `src/utils/aiConnectionErrors.ts`
- `src/hooks/settings/recommendedModels.ts`
- `oct-gateway/security/agent_permissions_policy.js` 里的纯判断逻辑

适合原因：

- 低风险
- 容易自动化
- 能提高后续重构安全性

建议先做测试，再做重构。

#### 3. 重复工具函数去重

当前可见重复点：

- `normalizeAgentPermissions`
- Google OpenAI Base URL 清洗逻辑
- 一些 provider/header/probe 相关逻辑在 gateway 内有重复

适合原因：

- 可以从“抽共享 helper”做起
- 行为目标明确：保持一致，不扩功能

注意：

- 先只去重纯函数
- 不要第一步就改调用链

### 中优先级：B 类任务

#### 4. `oct-gateway/gateway/slash.js` 模块化

现状：

- 文件很大
- 命令职责过多
- 内部存在可见重复逻辑

为什么不是 A 类：

- slash 命令直接面向用户
- 回归风险高
- 很多行为是“约定俗成”而非显式测试覆盖

推荐拆法：

1. 先只抽 `status` / `new conversation` / `probe` 相关纯辅助函数
2. 再按命令簇拆模块
3. 每拆一步都要手工跑关键命令

#### 5. `electron/main.ts` 的 helper 抽离

为什么只能算 B 类：

- 体积巨大，但不能一口气拆
- 里面夹杂窗口、IPC、网关、Nocturne、日志、任务、TTS
- 自动模式很容易“拆着拆着改坏顺序依赖”

安全做法：

只允许先抽三类纯 helper：

- 路径/配置 helper
- token / url / permission normalize helper
- log 解析 helper

不要一开始就让自动模式搬 IPC handler。

### 暂缓：C 类任务

#### 6. 整体拆 `electron/main.ts`

这是对的方向，但不适合直接扔给低配自动模式独立完成。

原因：

- 它需要先做模块边界设计
- 需要明确初始化顺序
- 需要处理大量共享状态
- 需要持续人工判定“是不是还兼容原行为”

正确做法：

- 先由人写模块蓝图
- 再把蓝图切成多个 A/B 子任务

#### 7. 重构聊天主链路

涉及：

- `src/ui/chat/ChatTab.v2.tsx`
- `src/hooks/useMessages.ts`
- 流式、FSM、活动时间线、权限、工具卡片

不建议直接交给自动模式的原因：

- 聊天链路隐式状态很多
- 用户体感回归不容易从测试里看出来
- 它很容易“代码更整齐，行为更脆”

#### 8. 跨 Frontend/Electron/Gateway 的统一配置架构改造

这类任务必须先有人做设计，再发施工单。

## 建议执行顺序

### 第一阶段：建立安全施工面

目标：

- 提高后续重构成功率
- 让自动模式先做不会伤主链路的工作

任务：

1. 给 `providerUtils` / `aiConnectionErrors` / `recommendedModels` 补测试
2. 收口设置面板的 provider 类型与元数据
3. 抽设置页 beginner/advanced 共用 helper

### 第二阶段：做低风险去重

任务：

1. 抽重复的 normalize helper
2. 抽 gateway 内重复 header/probe helper
3. 给抽出的 helper 补测试

### 第三阶段：受控模块化

任务：

1. 小步拆 `slash.js`
2. 小步抽 `electron/main.ts` 纯 helper
3. 每一步都人工 review

### 第四阶段：再决定是否进入大重构

触发条件：

- 关键逻辑已有最小测试兜底
- 模块边界已经通过前几轮抽取自然浮现
- 团队愿意投入人工 review 成本

若条件不满足，就不要急着拆主链路。

## 适合直接复制给自动模式的任务模板

### 模板 A：纯函数抽取

目标：只做无行为变化重构。

要求：

- 只修改指定文件
- 把重复纯函数抽到新 helper
- 不改调用语义
- 保持导出接口兼容
- 运行相关测试和构建
- 返回变更文件、验证结果、剩余风险

### 模板 B：补测试

目标：先补当前行为测试，不改业务逻辑。

要求：

- 只新增或修改测试文件
- 覆盖正常输入、边界输入、错误输入
- 不为了让测试通过而改生产逻辑
- 输出当前行为假设

### 模板 C：受控模块拆分

目标：只做文件结构调整，不改变用户可见行为。

要求：

- 先列出要抽出的函数名单
- 只抽名单内函数
- 不重写逻辑
- 不新增架构层
- 拆完后必须通过构建
- 输出可能存在的初始化顺序风险

## 不建议给自动模式的提示词

以下说法很危险：

- “你看看哪里能重构就都重构一下”
- “把这个大文件彻底拆干净”
- “顺便优化一下架构”
- “把相关逻辑都统一掉”
- “你自己判断最优方案”

这些说法默认要求模型承担设计与审核责任，超出了低配自动模式的稳定能力。

## 本轮建议结论

如果从明天开始实际投放自动模式额度，建议这样做：

1. 先连续做 3 到 5 个 A 类任务，建立可复用提示词模板
2. 再挑 1 个 B 类任务做试点，观察它在“人工审核门”下是否稳定
3. 暂时不要把聊天主链路和 `electron/main.ts` 全量拆分直接交给自动模式

一句话总结：

低配自动模式最适合做“清晰施工单”，不适合做“开放式重构负责人”。
