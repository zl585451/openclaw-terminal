## 1. 一句话定位

内容创作工作台不是单一的有声书改写功能，而是一个可扩展的内容制作多 Agent 平台。

当前 MVP 先跑通：

`小说原文 -> 多人演播有声书样章 -> 角色音标注 -> 演播设计 -> 质检交付`

未来可以继续扩展：

1. 广播剧 Agent 团队。
2. 短剧脚本 Agent 团队。
3. 作品分析 Agent 团队。
4. 图书馆 / 资料库侧的文本分析与检索 Agent。
5. 其他内容生产工作流。

## 2. 当前已经达成的核心共识

### 2.1 产品流程

创建任务阶段采用三步单屏确认，不再采用长页面滚动表单：

1. 第一步：确认素材。
2. 第二步：确认目标产物和处理范围。
3. 第三步：AI 初读后确认修改策略。

第三步确认后进入工作台，工作台第一屏不是技术调度台，而是面向小白用户的“开工确认书”。

### 2.2 用户体验原则

用户不需要理解 Agent 的输入对象、输出对象和内部技术链路。

用户第一视觉层级只需要看懂：

1. 谁在为我干活。
2. 分别负责什么。
3. 开工后我会拿到什么。
4. 系统不会乱改什么。
5. 哪些地方后面还需要我确认。

Agent ID、输入产物、输出产物、规则路径等技术信息默认折叠，供内部统筹、开发和高级用户查看。

### 2.3 后台流程原则

后台不是一次性把用户输入丢给大模型，而是分阶段生成对象、确认闸门和 Agent 计划：

`RawAsset -> SourceDocument -> SourceProfile -> IntakeReport -> TaskDraft -> TaskBrief -> AnalysisReport -> ModificationStrategy -> AgentExecutionPlan -> Artifact`

未通过确认闸门的内容只保存为草稿，不进入正式制作队列。

## 5. 当前 Agent 职能盘点

### 5.1 已有明确规则的 Agent

1. `task.intake_planner@1.0`
   任务安排初步分析 Agent，负责轻量判断素材、推荐目标和预分配 Agent。
2. `adapter.audiobook_text_rewriter@1.0`
   文本口语化改编 Agent，负责把小说改成适合多人演播的有声书台本。
3. `classifier.voice_role_marker@1.0`
   角色音分类标注 Agent，负责旁白、明确角色音、未定来源角色音、功能性声音和占位。
4. `designer.performance_audio@1.0`
   演播设计 Agent，负责 BGM、SFX、CV 情绪、气息、动作感和声场提示。
5. `reviewer.production_quality@1.0`
   质检 Agent，负责忠实度、可听度、人物度、连贯度、可执行度和节制度检查。

### 5.2 已纳入编排但仍可逐步实现的 Agent

1. `business.content_analyzer@1.0`
   AI 初读 / 业务分析 Agent，负责在第二步确认后输出问题、证据和修改策略建议。
2. `parser.source_document@1.0`
   文件解析 / SourceDocument 标准化 Agent 或服务。
3. `splitter.chapter_scene@1.0`
   章节、场景和片段切分 Agent。
4. `orchestrator.content_task@1.0`
   任务编排 Agent 或调度器，负责把确认结果转成 AgentExecutionPlan。
5. `packager.content_delivery@1.0`
   打包交付 Agent，负责整理最终交付包、交付清单和版本信息。

这些 Agent 不一定都要在 MVP 第一轮完整智能化，部分可以先用规则服务或 mock 服务承接。

## 6. 推荐的下一步计划

### 6.1 下一步优先级

Gateway mock 执行桥和 Track B 摘要服务已经接入，下一步应补齐最小执行状态机和真实 Agent 的第一个节点。

原因：

1. 单个业务规则已经足够支撑 MVP。
2. 前端已经验证 `AgentExecutionPlan -> AgentRun -> ArtifactEnvelope` 的基本体验。
3. 前端状态已具备跨组件共享基础，Gateway 也已具备推送执行事件和长文本摘要能力，下一步可以把 mock 节点逐步替换为真实 Agent。

### 6.2 建议新增文档

已新增两份文档：

1. `docs/02_architecture/内容创作Agent协议与编排规范.md`
   定义 Agent 注册表、上下文分发、串行 / 并行原则、确认闸门、状态机和 Artifact 存储。
2. `docs/03_specs/内容创作工作台/多人演播有声书Agent团队编排规范.md`
   定义有声书 MVP 的 Agent 团队、执行顺序、输入输出、可并行点、人工确认点。

后续如新增广播剧、短剧或图书馆共用 Agent，应继续按“平台协议 + 团队模板”的方式补文档。

### 6.3 建议实现顺序

以下顺序已整理为正式执行计划：

`docs/03_specs/内容创作工作台/内容创作工作台MVP执行计划.md`

1. 做 Gateway 最小执行状态机。
2. 将前端 mock 执行器下沉为 Gateway mock 执行服务。
3. 前端从 Gateway 读取 AgentRun / Artifact 状态。
4. 再接真实文件解析和 SourceDocument 持久化。
5. 最后接真实 Agent 调用和 Artifact 存储。

其中 1-3 的最小桥接已完成 MVP 骨架，Track B 摘要服务也已补齐离线基础测试。下一步建议优先做：执行记录持久化、取消/恢复、文本改编 Agent 真实调用。

## 7. 新模型接手工作流

新窗口或新 AI 接手时，建议按以下顺序阅读：

1. 先读本文件。
2. 再读 `README.md`。
3. 再读 `内容制作工作台UI结构规范.md`。
4. 再读 `内容创作工作台MVP执行计划.md`。
5. 再读 `内容创作任务创建双确认流程.md` 和 `内容创作任务对象模型.md`。
6. 如果要做架构，读 `docs/02_architecture/内容制作多Agent系统架构.md`。
7. 如果要做 Agent 协议或 Gateway 状态机，读 `docs/02_architecture/内容创作Agent协议与编排规范.md`。
8. 如果要做长文本摘要或真实 Agent 上下文压缩，读 `docs/02_architecture/summarizer-service.md`。
9. 如果要做有声书团队执行链路，读 `多人演播有声书Agent团队编排规范.md`。
10. 如果要接 Gateway 执行桥，读 `内容创作Gateway执行桥接协议.md`。
11. 如果要做具体有声书 Agent，读四份多人演播规则文档。
12. 如果要继续开发 UI，先查看 `src/modules/script-adapter/`。

接手后不要从零重设流程，除非明确要推翻当前设计。
