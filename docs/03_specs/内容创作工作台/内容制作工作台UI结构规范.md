# 内容制作工作台 UI 结构规范

## 文档状态

- 版本：v1.16
- 状态：当前定版，可作为内容制作工作台 V2 前端结构基线
- 生效方式：先用于工作台 MVP；当前已接入 Gateway mock 执行桥，真实 AI 和持久化后续接入
- 修订原则：先固定信息结构，再逐步接真实能力

---

## 1. 定位

内容制作工作台是面向创作者、制作统筹和审校人员的多 Agent 制作后台。

它不应被命名或设计为单一“有声书改写模块”。有声小说只是当前第一套团队模板，后续可继续扩展广播剧、短剧、漫画分镜等团队模板。

---

## 2. 当前 V2 范围

V2 先做前端骨架升级，并逐步接入 Gateway mock 执行桥：

1. 显示项目。
2. 显示团队模板。
3. 显示 Agent 流程。
4. 显示阶段输入输出。
5. 显示产物预览。
6. 显示 Agent 池。
7. 保留操作按钮占位。

V2 不做：

1. 真实 AI 调用。
2. 真实 AI Gateway 调用。
3. 数据库持久化。
4. 真实打回和重跑。
5. 最终 CV 分配。

---

## 3. 页面结构

工作台应包含三个主视图：

1. `工作台`
   左侧展示项目、章节和阶段列表，右侧展示当前阶段详情。
2. `团队流程`
   展示当前团队模板和横向 Agent 流水线。
3. `Agent 池`
   展示每个 Agent 的职责、输入产物、输出产物、规则文档和人工确认要求。

---

## 4. 信息层级

每个阶段详情应至少展示：

1. 阶段名称。
2. 阶段说明。
3. Agent 绑定。
4. 当前状态。
5. 输入产物。
6. 输出产物。
7. 规则文档。
8. 阶段产物预览。
9. 占位操作按钮。

---

## 5. 当前有声小说团队模板

默认模板为 `audiobook_multicast.v1`。

当前阶段顺序：

1. 项目摄入
2. 作品分析
3. 场景拆分
4. 文本改编
5. 角色音标注
6. 演播设计
7. 质检审核
8. 打包交付

---

## 6. 外观原则

1. 做成制作后台，不做营销页。
2. 信息密度适中，便于统筹扫读。
3. 用侧栏、流程线、详情面板、标签和产物列表承载信息。
4. 按钮只用于明确操作，不用大块装饰卡片制造视觉噪音。
5. 长中文标题和长规则路径必须能换行或截断，不得撑破布局。

---

## 7. V2.1 可读性落地规则

V2.1 的重点不是新增能力，而是把工作台从“开发调试面板”调整为“制作统筹可读界面”。

1. 页面主标题应优先表达当前项目和制作模板，不能让技术模块名占据第一视觉层级。
2. 阶段详情应优先展示业务信息，例如当前阶段、负责 Agent、输入产物、输出产物和人工复核要求。
3. 技术标识可以保留，但应降级展示，例如 `agent_id`、产物 key、版本号、token、运行时长等。
4. Agent 池应以角色职责为主标题，以技术绑定名为副信息，方便非工程成员理解分工。
5. 产物预览应使用中文制作摘要、片段示例或结构化要点，不应默认展示 JSON 调试文本。
6. 侧栏应分为项目、章节导航、制作阶段三个明确区域，避免信息堆在一起。
7. 当前阶段、已完成阶段、待处理阶段应有清晰的视觉差异，但不要依赖高饱和色块造成压迫感。
8. 规则文档、人工复核、可修改产物等信息必须可见，方便未来接入真实 Agent 后做人工确认和打回。

---

## 8. V2.2 任务式入口规则

V2.2 的重点是降低首次进入工作台的认知负担。默认工作台不再优先展示 Agent 内部结构，而是优先展示用户任务链路。

默认工作台应按以下顺序组织信息：

1. 当前任务：说明正在处理哪个项目、哪一章、当前处于哪一步。
2. 下一步操作：用一句话告诉用户现在该做什么，例如“确认 AI 初读分析，再决定怎么改”。
3. 任务说明：允许用户编辑本轮要求，例如样章范围、改编目标、保留边界。
4. AI 初读结论：先列问题，不直接改写，避免用户失去控制感。
5. 原文/结构依据：展示 AI 判断来自哪里，方便用户对照。
6. 建议改法预览：展示可采纳方向或样张片段。
7. 执行动作：提供明确按钮，例如采纳建议、补充意见、执行改写。

高级信息的处理原则：

1. `团队流程` 和 `Agent 池` 作为高级视图保留，但不作为默认首屏的主要认知入口。
2. token、运行时长、产物契约、规则路径等信息可以保留在阶段详情或高级视图中。
3. 默认工作台必须让非工程用户一眼知道“我现在能做什么”。
4. 每一轮 AI 输出都应支持用户确认、采纳、补充意见或打回，而不是自动进入下一阶段。

---

## 9. V2.3 主动创建入口规则

V2.3 的重点是支持用户不经过 AMY/Chat，主动进入 `内容创作` 面板创建任务。

入口应拆成三种状态：

1. `任务大厅`
   用户主动点击内容创作入口时，默认进入任务大厅，不直接进入工作台。
2. `创建任务向导`
   用户点击新建任务后，按素材来源、目标产物、处理范围、本轮要求逐步创建任务。
3. `任务工作台`
   用户点击开始分析后，进入 V2.2 定义的任务式工作台。

主动入口和 AMY 入口的区别：

1. AMY 入口已有上下文，例如用户刚上传文件或已经表达意图，所以创建面板可自动预填。
2. 主动入口没有上下文，所以必须先让用户选择素材来源、目标产物、处理范围和本轮目标。
3. 两种入口最终都应进入同一个任务工作台，不能维护两套制作流程。

主动创建任务向导的最小字段：

1. 素材来源：上传文件、粘贴文本、已有文档。
2. 目标产物：多人演播有声书、广播剧、短剧脚本、只做作品分析。
3. 处理范围：全文、前一章、自定义范围。
4. 本轮目标：先分析问题、直接生成样章、生成完整制作方案。
5. 特别要求：用户自然语言描述，例如不改剧情、口语化、标角色音、补音效。

第一版主动入口只做前端 mock 和路径确认，不接入真实上传、Gateway、AI 分析或持久化。

---

## 10. V2.4 任务要求边界规则

`填写本轮要求` 不应设计成完全无边界的自由输入框。它应是“结构化要求 + 可选补充”的组合。

界面边界：

1. 先提供推荐要求标签，例如不改剧情、提升听感、旁白口语化、标注角色音、补充 BGM 和音效。
2. 明确告诉用户应该填写什么：改编目标、处理范围、风格要求、保留边界、需要输出什么。
3. 明确告诉用户不要填写什么：大段原文、无关聊天、账号密码、要求 AI 改掉核心剧情事实。
4. 自由文本只作为补充说明，不直接无条件进入最终执行。
5. 文本框应有示例、建议字数和过短/过长提示。

执行边界：

1. 用户输入应先被整理为结构化任务摘要，再传给后续 Agent。
2. 与当前素材、目标产物、处理范围无关的内容应降级为备注，不进入改写执行。
3. 与已选择目标冲突的要求应在初读分析阶段提示用户确认。
4. 与作品事实冲突的要求不能直接执行，应标记为“可能改变大纲/剧情事实”。
5. 如果用户要求超出当前模板能力，例如让有声书任务生成视频分镜，应提示切换目标产物或新建任务。

---

## 11. V2.5 后台任务编排布局规则

V2.5 的重点是将创建任务页从“四宫格表单”调整为“后台任务编排台”。

创建任务页应按三栏组织：

1. 左栏：步骤导航、任务完整度、当前配置进度。
2. 中栏：当前主要配置内容，包括基础配置和本轮要求。
3. 右栏：任务摘要、即将执行的 Agent、执行边界。

操作区规则：

1. 主操作按钮应固定在底部操作栏中，不应被压在页面角落。
2. 底部操作栏应说明当前动作后果，例如“不会直接改稿，分析完成后仍需确认方向”。
3. `稍后再建`、`保存草稿`、`开始 AI 初读分析` 应作为不同强度的操作并列展示。

后台心智规则：

1. 页面应回答“当前走到哪一步”“系统理解成什么”“接下来会调用什么”。
2. 目标产物、处理范围等配置可以紧凑展示，不需要每项都占据大卡片。
3. 右栏摘要应实时承载未来 task schema 的可视化结果。
4. Agent 执行预览只表达调度意图，不代表已经执行真实后台任务。

---

## 12. V2.6 双确认创建规则

V2.6 的重点是把创建任务页定版为两个后台确认闸门，而不是一个自由表单。

创建任务页只保留两个主步骤：

1. `确认素材`
   用户提交原始文本，系统展示素材参数、文件解析状态和 Agent 预分配候选。用户点击确认后，才生成任务方案草案。
2. `确认执行`
   用户定义目标产物、处理范围、本轮目标和补充要求。系统展示即将锁定的 Agent 团队结构。用户点击确认后，才进入 AI 初读分析。

素材来源规则：

1. 第一版主入口为 `上传文件`，用于小说原文、章节文本、docx 或 md 文档。
2. `粘贴试跑` 作为轻量入口保留，适合短片段测试，不作为正式长文本制作的主路径。
3. `已有文档` 作为未来项目库入口保留，用于复用已解析文本、历史任务或用户资料库。
4. 三种来源最终都必须归一成同一个 `SourceDocument` 对象，后续 Agent 不直接关心来源 UI。

确认闸门规则：

1. 第一步确认后，系统生成素材参数、章节识别结果和 Agent 预分配，不直接执行改稿。
2. 第二步确认后，系统生成任务摘要、目标产物配置、执行边界和 Agent 团队结构。
3. 每个确认动作都应可落库、可回看、可被人工修改。
4. 未确认的内容只能作为草稿，不进入正式 Agent 执行队列。
5. 如果素材参数和用户要求冲突，例如素材不是小说却选择多人演播有声书，应在第二步前提示用户确认。

界面心智规则：

1. 页面要让用户清楚知道“现在是在确认输入”还是“现在是在确认执行”。
2. 不把上传、目标、范围、要求和 Agent 一次性铺满成同等权重。
3. 右侧摘要应展示后台即将形成的任务对象，而不是只做视觉装饰。
4. 底部操作栏只保留保存草稿、稍后再建和最终确认动作。

## 13. V2.7 当前步骤面板与右侧任务地图融合规则

V2.7 的重点是解决创建任务页中“当前步骤确认面板”和“右侧边栏”信息重复的问题。

信息职责应重新划分为：

1. 左侧栏：回答“当前走到哪一步”。
2. 中间主区：回答“这一步具体要确认什么”。
3. 右侧栏：回答“系统最终理解成什么、下一步会发生什么”。
4. 底部操作栏：回答“确认后会进入哪个动作”。

中间主区规则：

1. 第 1 步素材确认面板可以展示完整素材参数。
2. 第 1 步素材确认面板可以展示文件解析、内容识别、作品分析等预分配 Agent 的详情。
3. 第 2 步执行确认面板可以展示目标产物、处理范围、本轮要求和即将锁定的团队结构。
4. 当前步骤需要用户确认的内容，优先放在中间主区，不放到右侧重复展开。

右侧任务地图规则：

1. 右侧栏不再重复展示详细 Agent 列表。
2. 右侧栏展示任务摘要、确认闸门状态和 Agent 队列总览。
3. Agent 队列只显示数量和压缩状态，例如已预分配、即将执行、后续候选、人工确认。
4. 需要看 Agent 细节时，用户应回到当前步骤主面板或后续高级视图。

这样可以避免用户同时看到两组相似 Agent 信息，降低认知负担。

## 14. V2.8 初步分析回填第二步规则

V2.8 的重点是让第 2 步不再是空白规划表单，而是承接第 1 步确认后的后台轻量分析结果。

第 1 步确认后，后台应先完成：

1. 原始文件留存为 `RawAsset`。
2. 文本抽取、清洗和编码统一。
3. 标准文本保存为 `SourceDocument`。
4. 建立章节、段落和轻量索引，生成 `SourceProfile`。
5. 调用 `task.intake_planner@1.0` 任务安排初步分析 Agent。
6. 生成 `IntakeReport`、`TaskDraft`、`AgentPreAllocation` 和 `IntakeWarnings`。

第 2 步面板应展示三类信息：

1. `AI 初步判断`
   展示素材类型、结构判断、推荐目标和风险提示。
2. `推荐执行方案`
   展示推荐范围、推荐本轮目标和推荐后续 Agent。
3. `用户最终确认`
   保留目标产物、处理范围、本轮目标、要求标签和补充输入，允许用户基于 AI 建议调整。

时效规则：

1. 第 1 步后的任务安排 Agent 应控制在 5-20 秒为主。
2. 长文本最多不应让用户等待超过 60 秒。
3. 超过 60 秒时，应返回部分结果，并把深度处理放入后台队列。
4. 业务分析 Agent 必须放在第 2 步确认之后执行，避免上传后直接进入漫长等待。

---

## 15. V2.9 任务方案确认单规则

V2.9 的重点是降低第 2 步的认知负担。第 2 步不再表现为“完整配置表单”，而应表现为“AI 已拟好方案，用户确认是否执行”。

第 2 步主路径只确认四件事：

1. 目标产物：例如多人演播有声书、广播剧或只做作品分析。
2. 处理范围：例如第 1 章、全文或自定义范围。
3. 改动权限：例如不改剧情、只提升听感，或允许结构重写。
4. 下一步 Agent：例如业务分析 Agent、文本改编 Agent 或任务安排 Agent。

界面规则：

1. `AI 初步判断` 应压缩成一行系统判断或一句摘要，不再用多张大卡片展示。
2. `推荐执行方案` 应作为主视觉，让用户先看到“系统建议下一步做什么”。
3. 目标、范围、本轮动作等细项可以保留，但应进入“微调设置”或次级区域。
4. 推荐标签和自由输入只作为补充要求，不应抢占主路径。
5. 用户主动作应是“确认方案，开始分析”，而不是让用户逐项填写所有字段。

业务衔接规则：

1. 第 1 步确认后生成 `TaskDraft`，第 2 步展示的是 `TaskDraft` 的可读确认版。
2. 用户在第 2 步修改的内容应回写到 `TaskBrief` 和 `AgentPlan`。
3. 如果用户不修改，系统按推荐方案直接进入下一步 Agent。
4. 如果用户补充要求和推荐方案冲突，应在进入执行队列前触发确认提示。

---

## 16. V2.10 第一步到第二步 mock 业务链路规则

V2.10 的重点是让用户可以试走“确认素材 → 后台摄入 → 生成任务方案 → 回填第二步”的完整链路。

第一版不接真实上传、真实文件解析和真实 Gateway，而是提供可替换的 mock executor。mock executor 必须模拟真实业务对象和状态，而不是只切换 UI。

链路状态：

1. `idle`：等待用户确认素材。
2. `running`：正在执行素材摄入和任务草案生成。
3. `completed`：已生成 `IntakeResult`，第二步可确认执行方案。
4. `failed`：摄入失败，允许用户重试。

mock 摄入步骤：

1. `RawAsset` 原始文件留存。
2. 文本抽取、清洗和编码统一。
3. `SourceDocument` 标准化入库。
4. `SourceProfile` 建索引和轻量画像。
5. 任务安排 Agent 生成 `TaskDraft`。

产物规则：

1. 第一步确认后应生成 `IntakeResult`。
2. `IntakeResult` 应包含素材参数、系统判断摘要、推荐执行方案、确认项和 Agent 预分配。
3. 第二步页面不直接读取散落常量，而应读取 `IntakeResult`。
4. 右侧任务地图应随 `IntakeResult` 的状态变化，而不是固定展示 mock 文案。

替换边界：

1. 当前 `runMockTaskIntake` 只模拟本地耗时和返回对象。
2. 未来接真实后台时，应保持 UI 消费的 `IntakeResult` 结构稳定。
3. 如果真实后台返回更多字段，可以在 `IntakeResult` 上扩展，不要让 UI 直接依赖底层文件解析细节。

---

## 17. V2.11 四项确认卡交互规则

V2.11 的重点是让第 2 步四张确认卡可交互，并明确“AI 预填、用户可改、系统控边界”的产品心智。

四张确认卡不应设计成纯自由输入，也不应写死为固定模板。它们应来自 `TaskDraft.confirmItems`，每张卡至少包含：

1. `id`：结构化字段标识。
2. `label`：展示名称，例如目标产物、处理范围、改动权限、下一步 Agent。
3. `value`：AI 推荐默认值。
4. `desc`：当前值的解释。
5. `options`：同类候选项。
6. `customHint`：自定义补充提示。

交互规则：

1. 默认只展示 AI 推荐结果，避免用户一开始就面对大量选项。
2. 用户点击“修改”后，在当前卡片内展开候选项。
3. 候选项应区分 `AI 推荐`、`同类预设`、`Agent 候选`。
4. 用户选择候选项后，卡片主值应即时更新。
5. 自定义输入只作为补充约束，不直接覆盖结构化字段。
6. 下一步 Agent 不建议用户手写，应优先从候选 Agent 中选择。

不同文本类型的扩展规则：

1. 小说：目标产物可包含多人演播有声书、小说润色、剧情重写、作品分析。
2. 演讲稿：目标产物可包含演讲稿润色、口播稿优化、PPT 讲稿、短视频口播。
3. 论文：目标产物可包含学术润色、结构建议、降 AI 味、摘要改写、投稿意见整理。
4. 改动权限应是等级化候选，例如只分析不改、轻度润色、中度改写、重度重写、结构重建。

## 18. V2.12 执行确认减负规则

本节为历史迭代记录。V2.13 已覆盖本节中的“三项确认”方案，创建阶段不再确认改动边界。

V2.12 的重点是继续降低第 2 步认知负担。第 2 步不再让用户同时面对推荐卡、预设标签、自由输入和高级微调区，而是收敛为“AI 推荐方案 + 三项确认 + 可选补充”。

第 2 步只保留三项用户必须确认的结构化内容：

1. 工作目标：例如多人演播有声书先做业务分析、小说润色先做问题分析、剧情重写先做结构诊断。
2. 处理范围：例如第 1 章、第 1 章前半段、全文或自定义范围。
3. 改动边界：例如不改剧情只提升听感、轻度润色、中度改写、重度重写、只分析不改。

界面减负规则：

1. 删除下方重复的推荐要求标签，避免和三张确认卡重复表达。
2. 删除“需要微调目标、范围或本轮动作”的高级自选区，避免用户误以为必须重新配置一遍任务。
3. 自由输入只保留一个“可选补充说明”，用于补充三张确认卡没有覆盖的边界。
4. 补充说明可以留空，不应阻塞用户进入下一步。
5. 右侧任务地图只做结果摘要，不再承载另一套可编辑配置。

Agent 分配规则：

1. 下一步 Agent 由 `TaskDraft` 和 `AgentPreAllocation` 自动生成，不作为用户必须选择的确认卡。
2. 用户可以看到即将执行的 Agent 和后续候选队列，但不在第 2 步手动挑选 Agent。
3. 如果用户修改工作目标、处理范围或改动边界，系统可以重新生成任务方案，而不是让用户直接改 Agent 队列。
4. `TaskDraft.confirmItems` 在当前版本只应包含工作目标、处理范围和改动边界，不包含 `next_agent`。

后台心智规则：

1. 第 2 步的核心问题是“这个方案能不能执行”，不是“用户自己设计一套流程”。
2. 用户只负责确认业务意图和边界，系统负责把意图翻译成 Agent 团队和执行顺序。
3. 与三项确认内容冲突的补充说明，应在正式执行前触发人工确认或重新生成方案。

## 19. V2.13 创建阶段两步确认规则

V2.13 修正 V2.12 中仍然把“改动边界”放在创建阶段的问题。创建阶段只确认“做什么”和“做哪里”，不确认“怎么改”。

创建阶段只保留两个确认闸门：

1. `确认素材`
   确认文件、章节、文本类型和基础解析结果。
2. `确认目标和范围`
   确认目标产物和工作范围，例如多人演播有声书、第 1 章、某一段文本。

第二步只保留两张结构化确认卡：

1. 工作目标：确认产品内容和分析方向，例如多人演播有声书、小说润色、剧情重写、只做作品分析。
2. 处理范围：确认第几章、哪一段、全文或自定义范围。

第二步不应出现：

1. 改动权限。
2. 改写深度。
3. 不改剧情、轻度润色、重度重写等策略选择。
4. 角色音、BGM、演播设计等执行细项。

第三步应在 AI 初读分析完成后出现：

1. AI 展示文本问题、风险和可修改建议。
2. 用户再选择修改策略，例如只分析不改、轻度润色、听感改编、结构调整、剧情重写。
3. 第三步确认后，才进入文本改编、角色音标注、演播设计等后续 Agent。

边界原则：

1. 创建阶段解决“任务对象成立不成立”。
2. 分析阶段解决“文本有什么问题”。
3. 修改策略阶段解决“到底怎么改、改到什么深度”。
4. 这样可以避免用户在没有分析结果前盲选改动权限，也减少目标和权限之间的冲突。

## 20. V2.14 素材归属驱动目标候选规则

V2.14 明确第 2 步的目标选项必须来自第 1 步 AI 对素材归属的判断，而不是展示全量产品模板。

第 1 步 AI 初步分析必须输出：

1. `contentCategory`：素材归属，例如小说正文、论文、演讲稿、剧本、课程稿。
2. `structureSummary`：结构判断，例如已识别第 1 章、包含对白、包含小标题、包含引用等。
3. `recommendedDirections`：适配当前素材的候选产品方向。
4. `unsupportedDirections`：不建议出现的产品方向及原因。
5. `confidenceLabel`：归属判断可信度。

第 2 步 UI 规则：

1. 只展示 `recommendedDirections` 中的方向。
2. 不展示与素材归属不匹配的方向。
3. 不适配方向可以作为说明展示，但不能作为默认可点选项。
4. 第二步只确认产品方向和工作范围，不提供自由补充大文本框。
5. 如果用户必须跨类型制作，应提供“重新生成方案”或“人工确认跨类型任务”，不在默认候选中混入不适配方向。

示例：

1. 小说正文可以展示多人演播有声书、广播剧、小说润色、作品分析。
2. 论文可以展示论文润色、结构建议、摘要改写、投稿意见整理，不展示多人演播有声书。
3. 演讲稿可以展示演讲稿润色、口播稿优化、PPT 讲稿、短视频口播，不展示广播剧。

后台规则：

1. `TaskDraft.confirmItems.work_goal.options` 必须由 `SourceProfile.recommendedDirections` 映射生成。
2. `TaskDraft.confirmItems.scope.options` 必须由章节识别、段落切分或用户选区生成。
3. 第二步确认后得到的核心参数是 `OutputTarget` 和 `WorkScope`。
4. 拿到这两个参数后，系统才进入对应业务分析 Agent，生成第三步的细节定义和修改策略建议。

## 21. V2.15 AI 初读分析与修改策略确认规则

V2.15 将第三步落实为可交互 UI：用户确认目标和范围后，系统先运行 AI 初读分析，再让用户选择修改策略。

第三步必须展示五类信息：

1. `AI 初读结论`
   用一段短文总结当前文本的问题、风险和推荐方向。
2. `问题诊断`
   按卡片展示问题类型、严重程度和说明。
3. `问题证据`
   展示原文位置、原文片段和问题说明，让用户能对照判断。
4. `修改策略选项`
   根据第二步的产品方向生成，例如只分析不改、轻度听感润色、有声书样章制作、广播剧可行性拆解。
5. `执行影响`
   展示确认策略后会进入哪些 Agent、生成哪些产物、是否需要人工复核。

交互规则：

1. 第二步按钮点击后不直接进入工作台，而是进入 `AI 初读分析中` 状态。
2. 分析完成后自动回填第三步面板。
3. AI 推荐策略应默认选中，但用户可以切换。
4. 用户确认策略后，才进入制作工作台或后续 Agent 队列。
5. 第三步仍然不要求用户写大段自由文本，避免把决策重新变成开放表单。

后台对象：

1. `AnalysisReport`：AI 初读报告。
2. `ModificationStrategy`：用户确认的修改策略。
3. `ExecutionImpact`：策略确认后的执行影响。
4. `AgentExecutionPlan`：后续制作 Agent 队列。

## 22. V2.16 进入工作台后的执行单视图规则

V2.16 明确：用户在第三步确认修改策略后，进入工作台看到的默认页面不应再是二次确认页面，而应是“任务执行总览页”。

进入工作台后的页面必须回答四件事：

1. `任务已经锁定什么`
   展示产品目标、处理范围、修改策略和人工复核点。
2. `接下来谁来执行`
   展示后续 Agent 队列，包括状态、输入、输出和是否需要人工复核。
3. `本轮会交付什么`
   展示样章台本、角色音标注表、演播设计稿、质检报告和交付包等产物预期。
4. `执行边界是什么`
   展示不做什么、重点做什么、交给人工确认什么。

界面规则：

1. 不再展示大段自由填写任务要求。
2. 不再出现“先确认 AI 第一轮分析，再决定怎么改”的提示。
3. 主按钮应变成执行型，例如启动第一轮制作、查看执行队列、打开当前执行阶段。
4. 已确认的第三步策略应转译为任务执行单，而不是要求用户重复确认。
5. 如果用户需要回到前置确认，应作为次级入口，不占据默认主路径。

后台对象规则：

1. 第三步确认后应生成 `TaskExecutionSheet`。
2. `TaskExecutionSheet` 应包含 `OutputTarget`、`WorkScope`、`ModificationStrategy`、`AgentExecutionPlan`、`ExpectedArtifacts` 和 `ReviewGates`。
3. 工作台默认读取 `TaskExecutionSheet`，而不是重新读取用户自由输入。
4. 真实执行接入前，前端可以用 mock stage 和 artifact 数据模拟任务执行单。

## 23. V2.17 创建确认页单屏转跳规则

V2.17 明确：创建确认页不应把第 1、2、3 步全部纵向铺开成一篇长文档，而应采用单屏转跳式 Wizard。

核心规则：

1. 默认只展示当前步骤卡片。
2. 第 1 步确认素材完成后，自动切到第 2 步。
3. 第 2 步确认目标和范围后，自动切到第 3 步，并显示 AI 初读分析中状态。
4. 第 3 步分析完成后，在同一屏展示 AI 初读结论、证据和修改策略选择。
5. 第 3 步确认后，进入工作台执行单视图。

交互规则：

1. 左侧步骤导航保留，但只用于显示当前进度和回看已完成步骤。
2. 未满足前置条件的步骤不可点击。
3. 已完成步骤可以回看；未来真实业务中，修改已完成步骤应触发后续方案重新生成。
4. 底部固定操作栏只服务当前步骤，按钮文案必须随当前步骤变化。
5. 右侧任务地图只做摘要和状态反馈，不承载另一套可编辑表单。

心智边界：

1. 创建确认页是“逐步定任务”，不做执行总览。
2. 工作台页是“看系统执行”，不再反复让用户确认前置任务。
3. 单屏 Wizard 的目标是减少滚动查找和选择焦虑，让用户始终知道当前只需要确认一件事。

## 24. V2.18 开工确认书视图规则

V2.18 将第三步确认后的默认工作台入口，从“执行总览页”调整为“开工确认书”。该页面更接近用户签署制作合同前的最后确认，而不是后台调度面板。

核心定位：

1. 用户不需要理解 Agent 的输入产物、输出产物、规则路径和技术 ID。
2. 用户需要知道谁在帮他干活、分别负责什么、启动后会拿到什么、系统不会乱改什么。
3. 默认页面应降低焦虑，让用户放心点击“确认开工”。

默认信息结构：

1. `开工确认书 Hero`
   展示任务已经准备好开工，并用“不会改剧情、先做样章、人工复核”等确认章建立信任。
2. `三项核心确认`
   展示做什么、做哪里、怎么改。
3. `需要用户之后确认的地方`
   展示角色音回绑、演播标注、质检结果等后续人工确认点。
4. `谁在为你干活`
   用制作角色表达 Agent，例如文本改编师、角色音统筹、演播设计师、质检审校、交付打包员。
5. `开工后会拿到什么`
   用交付清单展示样章台本、角色音标注表、演播设计稿、质检报告、交付包。
6. `保护条款`
   展示不会改核心剧情、不会提前解释悬疑、不会乱归角色音。

技术信息规则：

1. Agent ID、输入产物、输出产物、技术状态和锁定依据默认折叠。
2. 技术细节通过“查看技术细节”入口保留，供内部统筹、开发和高级用户查看。
3. 默认不把 `scene_breakdown`、`plot_lock`、`adapted_script` 等 key 暴露给普通用户。
4. 技术细节不得抢占开工确认页的主视觉锚点。

文案规则：

1. 主按钮使用“确认开工”，弱化工程感。
2. “Agent 队列”默认改写为“谁在为你干活”。
3. “执行边界”默认改写为“保护条款”。
4. “产物输出”默认改写为“开工后你会拿到什么”。
