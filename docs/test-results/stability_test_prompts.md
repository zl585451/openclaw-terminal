# OCT AI 输出格式稳定性压测口令集

> **目的**：测试 AI 是否能严格遵守 `OCT_PROTOCOL.md` 和 `RENDER_PROTOCOL.md`，特别是针对「胶囊按钮（Pill）」的自动检测防御以及成对标签的嵌套稳定性。

---

## 🧪 测试口令一：结构化组件混合压测（针对「胶囊外溢」）

**测试目的**：验证 AI 是否能正确处理「普通正文 + 代码块 + 表格 + 交互胶囊」的混合排版，而不发生渲染错位。

**发送给 AI 的口令：**
```text
请帮我分析一下当前 OCT 项目的渲染协议优化方案。
要求：
1. 先用一段文字简述协议 V2 的核心。
2. 给出一段 TypeScript 代码示例，展示如何定义一个 RenderSegment 类型。
3. 对比 PillOptionBox 和 QuestionCards 的三个维度差异，用 Markdown 表格呈现。
4. 在回复最后，用 [pills] 标签提供三个选项：■ 深入代码实现、■ 查看测试用例、■ 暂时不需要。
注意：严禁在代码块或表格中使用裸露的 ■ 符号，确保交互选项只出现在末尾的标签内。
```

**✅ 预期表现：**
- 代码块、表格渲染正常。
- 只有末尾出现交互胶囊。
- 胶囊内不含 `[pills]` 标签文字。

---

## 🧪 测试口令二：自动检测防御测试（防止「误触胶囊」）

**测试目的**：压测前端 `optionBoxParser.ts`。测试当 AI 在描述协议本身（提到符号）时，是否会错误地把解释文字变成按钮。

**发送给 AI 的口令：**
```text
我想学习一下 OCT 的渲染协议。请详细解释一下：
1. 什么是符号检测模式？请列出它支持的所有符号（如 ■, ●, ◆ 等）。
2. 为什么在正文中直接写 "■ 选项" 会被误识别？
3. 如何使用 [text] 标签来保护一段包含上述符号的内容不被误识别为按钮？
请在回复中多次使用这些符号进行举例说明，但不要触发任何真正的交互按钮。
```

**✅ 预期表现：**
- 所有的符号都应该作为纯文本显示在 Markdown 里。
- **不应**出现任何可以点击的胶囊按钮或选项框。
- 如果 AI 聪明，它会使用 `[text]` 标签或代码块来保护这些符号。

---

## 🧪 测试口令三：InlineInquiry (clarify_card) 极端压测

**测试目的**：测试 JSON 协议稳定性、字段 Label 的问句化要求，以及多维度的承载能力。

**发送给 AI 的口令：**
```text
我想发起一个全新的「周报自动化」子项目，但我现在思路很乱。
请通过 [clarify_card] 询问器向我收集以下维度的信息：
1. 目标平台（单选：钉钉、飞书、企业微信、自定义）。
2. 自动化频率（多选：每日、每周、每月）。
3. 核心功能描述（自由文本）。
4. 是否需要接入 AI 自动润色（确认型选项）。
要求：
- label 必须是完整的问句。
- 严格遵循 JSON 格式。
- 回复中除了标签外，只允许有一句简单的引导语。
```

**✅ 预期表现：**
- 输入框上方弹出内联询问器。
- JSON 没有任何语法错误（否则前端会白屏或显示原始 JSON）。
- 每个分页的标题都是问句。

---

## 🧪 测试口令四：任务清单 vs 复选框 边界测试

**测试目的**：验证 AI 是否能分清 `TaskList`（用户待办）和 `OptionBox`（告诉 AI 的选项）。

**发送给 AI 的口令：**
```text
帮我制定一个修复 Bug 的流程，并列出我接下来需要执行的任务清单。
同时，在清单下方，请问我是否需要你提供相关的代码模板，并给出两个胶囊选项。
```

**✅ 预期表现：**
- 任务清单应该渲染为 `TaskList`（带进度条，勾选不发送消息）。
- 下方的胶囊选项应该渲染为 `PillOptionBox`（点击即发送）。
- 两者互不干扰。

## 📊 稳定性判定标准（Done 准则）

| 表现描述 | 判定 |
| :--- | :--- |
| 交互元素出现在不该出现的地方（如代码块内变成按钮） | ❌ 不稳定 |
| 原始协议标签（如 `[pills]`）原样泄露在正文中 | ❌ 不稳定 |
| 点击胶囊后，发送的内容包含多余的符号或标签 | ❌ 不稳定 |
| 长时间流式输出过程中，UI 剧烈闪烁或布局崩坏 | ❌ 不稳定 |
| **符合协议，结构清晰，交互组件仅在指定区域生效** | **✅ 稳定** |
