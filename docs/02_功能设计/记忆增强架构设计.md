# OCT 记忆增强架构设计

> 基于苏格拉底式需求梳理后的架构分析与设计方案

---

## 〇、已集成：Nocturne Memory（2026.3）

OCT 已集成 [Nocturne Memory](https://github.com/Dataojitori/nocturne_memory) 作为长期记忆方案。

### 使用步骤
1. 确保已安装 **Python 3.x**
2. 打开 **设置** → 找到 **Nocturne 记忆系统** 区块
3. 点击 **安装 Nocturne 依赖**，等待 pip 安装完成
4. **重启 Gateway**（停止后重新启动），Agent 即可使用 Nocturne 记忆

### 技术实现
- Nocturne 位于 `resources/nocturne_memory`，随 OCT 打包
- `~/.openclaw/openclaw.json` 自动注入 `nocturne_memory` MCP 配置
- Agent AMY 默认启用 `mcpServers: ["nocturne_memory"]`
- 数据库：`userData/nocturne_memory.db`（SQLite）

### 管理界面
- Nocturne 提供 Web Dashboard（需单独启动 `uvicorn`）用于可视化管理记忆
- 项目地址：<https://github.com/Dataojitori/nocturne_memory>

## 一、现有架构概览

### 1.1 消息流

```
用户输入 → ChatTab → IPC openclaw-send → main.ts sendChatMessage()
    → WebSocket chat.send(sessionKey, message, attachments) → Gateway
    → Agent (AMY) → 大模型 → 回复流式返回
```

**关键点**：OCT 只负责把「纯文本 + 附件」发给 Gateway，**没有任何记忆相关逻辑**。

### 1.2 你关心的能力（问题 8）

| 能力 | 现状 | 可扩展点 |
|------|------|----------|
| **C. 自动提炼** | 无 | OCT 可在收到回复后，从对话中提取重要信息并写入本地 |
| **D. 检索增强** | 无 | OCT 可在 `sendChatMessage` 发送前做本地检索，把结果注入消息 |

### 1.3 OCT 已有的「记忆相关」能力

| 能力 | 位置 | 用途 |
|------|------|------|
| 对话历史 | `~/.openclaw/claw-terminal-history.json` | 保存最近 100 条消息，供界面展示 |
| 会话状态 | `session-state.json` (userData) | 保存 messages、sessionKey |
| sessionKey | 环境变量 `OPENCLAW_SESSION_KEY` 或默认 `main` | 标识当前会话，Gateway 侧关联 |

**结论**：OCT 有「对话级」存储，**没有**长期记忆、语义检索、自动提炼。

### 1.4 OpenClaw / Gateway 的记忆能力（服务端）

- **memory_search**：语义检索，在 Markdown 记忆文件中查找相关片段  
- **memory_read**：按 ID 读取完整记忆内容  
- 存储：`~/.openclaw/` 下 Markdown 文件  
- 检索：向量 + 关键词混合，maxResults 可配置（如 8 条）  
- 控制：`chat.options.no_memory` 可关闭某次请求的记忆（当前 OCT 未使用）

**痛点来源**：  
漏读、检索不准、速度慢、容量截断，主要来自 **Gateway 侧 memorySearch** 的读取式设计；OCT 目前无法参与。

## 二、OCT 可参与的「记忆增强」方案

### 2.1 架构原则（问题 7：先看架构能支持什么）

基于现有实现，OCT 可以安全地做两件事，且**不依赖 Gateway 改协议**：

1. **发送前注入**：在 `finalMessage` 里拼接本地检索结果（如 `[OCT 本地记忆]\n...`）
2. **回复后提炼**：从完整对话中提取要点，写入本地 Markdown，供 Gateway memorySearch 下次索引

### 2.2 方案 D：检索增强（OCT 发请求前本地检索）

**思路**：在 `sendChatMessage` 中，先对用户消息做本地检索，把相关记忆拼进 `finalMessage`，再发给 Gateway。

```
用户消息 → OCT 本地记忆检索（语义/关键词）→ 拼接 "[相关记忆]\n{检索结果}\n\n[用户消息]\n{原文}"
    → chat.send → Gateway
```

**OCT 需要**：

- 本地记忆库：如 `~/.openclaw/oct-memory/` 下 Markdown 文件
- 检索实现二选一：
  - **轻量**：关键词 + 简单 TF/BM25，无外部 API
  - **语义**：本地 embedding 或调用已有 embedding 服务
- 可配置：开关、maxResults、是否注入到消息

**收益**：

- 减少漏读（A）：多一层本地召回，补足 Gateway 漏掉的内容
- 提高准确度（B）：可加用户反馈、关键词加权
- 更快（C）：本地检索，减少对 Gateway 记忆查询的依赖
- 可追溯（D）：检索结果可展示在 UI（如「本次使用了以下记忆」）

### 2.3 方案 C：自动提炼（OCT 从对话中提取并存储）

**思路**：每次对话结束后，OCT 调用「提炼逻辑」从 user+assistant 中抽取关键信息，追加到本地 Markdown。

```
对话结束 → 提炼服务（规则 / 小模型 / 用户确认）→ 写入 ~/.openclaw/oct-memory/*.md
    → Gateway memorySearch 监听目录变更 → 自动索引
```

**OCT 需要**：

- 提炼逻辑：规则模板 或 调用本地/远程小模型
- 存储格式：与 OpenClaw memorySearch 兼容的 Markdown（含 frontmatter 更佳）
- 与 Gateway 共用 `~/.openclaw/` 或子目录，便于 memorySearch 纳入

**收益**：

- 减少漏读（A）：更多「重要信息」被写入记忆，后续可被检索
- 可控制（B）：可做「保存这条」/「忽略」的快捷操作
- 可追溯（D）：每条记忆有来源（时间、对话 ID）

## 四、建议实施顺序

### 阶段 0：准备（问题 7 的落实）

1. 确认 Gateway 的 memorySearch 配置（`~/.openclaw/config.json`）  
2. 确认记忆文件路径（如 `memory/` 或 `oct-memory/`）  
3. 决定 OCT 记忆目录：与 Gateway 共用 vs 独立目录  

### 阶段 1：检索增强（D）— 优先

- 实现本地记忆目录 + 轻量检索（关键词）
- 在 `sendChatMessage` 前调用检索，可选注入到 `finalMessage`
- 配置开关：`octMemory.retrievalEnabled`、`octMemory.maxResults`

### 阶段 2：自动提炼（C）

- 定义提炼规则 或 集成小模型
- 对话结束时写入 Markdown
- 与 Gateway memorySearch 目录对齐，确保会被索引

### 阶段 3：可控制、可追溯（D 的 UI）

- 「记住这条」：选中消息 → 保存到记忆
- 「忘记」：从记忆列表中删除
- 「本次用到的记忆」：在回复区域展示检索到的片段

## 五、技术约束与风险

| 约束 | 说明 |
|------|------|
| chat.send 当前参数 | 仅有 `sessionKey, idempotencyKey, message, attachments`，无法单独传「记忆上下文」 |
| 注入方式 | 只能通过把检索结果拼进 `message` 实现，会占用上下文 token |
| 语义检索 | 若用 embedding，需要额外 API 或本地模型 |
| 提炼质量 | 规则提炼简单但粗糙；小模型需要额外依赖和配置 |
