# 图形输出路由策略

> 状态：CURRENT  
> 最后更新：2026-04-10  
> 用途：说明用户提出“画图/整理成图/做图表”时，系统如何在聊天区、Canvas 和文档之间分流。

---

## 目标

OCT 不是专业制图软件。

它的目标是：

- 文本说明足够专业
- 图形输出半专业、稳定、够清楚
- 简单图直接在聊天区看
- 复杂图进入 Canvas
- 多图或多部分解释优先组织成文档成果物

---

## 三层分工

### 1. 用户层：只表达结果需求

用户通常会表达：

- 帮我画个流程图
- 给我一个结构图
- 做个占比图
- 用图和说明整理一下

用户不需要也不应该决定：

- Mermaid
- react-flow
- echart

这些是系统内部实现细节。

### 2. 产品层：决定结果容器

产品层只决定：

- 聊天区小图
- Canvas 图
- Markdown / Canvas 文档
- 表格

### 3. 实现层：内部选择图形引擎

系统内部再决定使用：

- Mermaid
- react-flow
- echart

---

## 路由规则

### A. 聊天区小图

适合：

- 轻量流程图
- 简单判断图
- 很小的单根层级图

要求：

- 节点少
- 主线明确
- 一眼能懂

系统内部通常使用 Mermaid。

### B. Canvas 图

适合：

- 结构图
- 架构图
- 组件关系图
- 依赖图
- 分层关系图
- 较复杂的流程图
- 数据图表

系统内部可能使用：

- react-flow
- Mermaid
- echart

但这些不应成为用户正文里的主叙述。

### C. Markdown / Canvas 文档

适合：

- 多图解释
- 分章节说明
- 图 + 文本 + 表格混合输出
- “完整讲解一下系统”这类请求

---

## 当前推荐边界

### 聊天区优先

- 简单流程图
- 轻量判断链
- 轻量层级树

### Canvas 优先

- 专业结构图
- 架构分层图
- 多模块系统关系
- 复杂跨层连接
- 数据图表

### 文档优先

- 多图任务
- 完整方案
- 图文并重讲解

---

## 为什么要隐藏底层工具

如果把 Mermaid / react-flow / echart 暴露给普通用户，会带来这些问题：

- 用户被迫理解实现术语
- 用户以为自己需要指定工具
- AI 更容易围绕工具名回答，而不是围绕结果需求回答

因此更好的策略是：

- 用户说“我要什么结果”
- 系统自己选择“用什么实现”

---

## 当前已知问题

1. 简单层级图有时仍会被过度送去 Canvas
2. 简单流程图阈值仍偏保守
3. 多图任务还需要更稳定地收敛到文档成果物
