# OmniRoute 最小逻辑能力设计 (Phase 1)

本文档定义了 OmniRoute 架构的核心抽象——逻辑能力别名（Logical Capability Aliases），并明确了它们的覆盖范围、边界以及当前设计决策的背后原因。

## 1. 最小逻辑能力定义

在第一阶段中，OmniRoute 仅抽象并设计以下三条最基础的能力别名：

| 能力别名 | 范围 | 不包含 |
|---|---|---|
| `oct-chat` | 主聊天、普通问答、状态重写、低成本、低延迟的交互对话。 | 任何形式的工具调用、多模态读图 (Vision)、向量化 (Embedding)、以及图片生成。 |
| `oct-plan` | 快速规划、文本摘要、工具结果压缩、结构化数据提取、复杂任务拆解和工作流中继。 | 工具的物理执行、跨供应商的多层级 Fallback 自愈。 |
| `oct-tool-safe` | 依赖工具调用（Tool Calling / Function Calling）的主工具循环、智能体任务执行。 | 第一阶段不接入真实主流程，只做选择策略与候选集定义。 |

---

## 2. 核心架构决策与说明

### 2.1 为什么第一阶段不拆分 `oct-plan-fast` 与 `oct-plan-deep`？
1. **防止过度设计与配置膨胀**: 
   大语言模型在规划（Planning）和结构化输出（Structured Extraction）上的能力阶梯虽然存在，但在第一阶段，OCT 系统的配置及模型预设（如 `qwen3.5-plus`、`deepseek-v4-flash`）已经足够覆盖大多数常规规划和摘要任务。
2. **便于映射集约化**:
   如果在此刻就将规划拆分为 fast 和 deep 两层，将会导致映射草案（Mapping Draft）极其臃肿，并且在用户没有配置足够多的独立 Key 时，两套映射最终仍会退化并指向相同的物理模型，增加了无谓的解析成本。

### 2.2 为什么 `oct-vision` 和 `oct-embed` 暂缓设计？
1. **协议/端点非标准化**:
   - **Embedding**：物理端点为 `/embeddings`（而非 `/chat/completions`），输入、输出 Schema（浮点向量数组 vs choices content）完全不同，无法纳入通用的 OmniRoute 软路由调度。
   - **Vision**：在 payload 层面存在大量的 Base64 图片组装逻辑、图片本地临时文件生命周期管理。
2. **高耦合与强场景绑定**:
   - 向量检索（Embedding）深度绑定了 Nocturne 记忆服务器及本地向量数据库（Python/js 模块）。
   - 图片分析（Vision）作为旁路非阻塞调用，失败时直接优雅降级（Fallback to user prompt），其调用链路不参与普通对话的耗时和限流计数。
   因此，将这两个极度特化的能力维持在现有的独立读取位置，能极大减小一阶段主流程的回归测试风险。

### 2.3 为什么工具调用能力 (`oct-tool-safe`) 必须与普通聊天模型切换完全隔离？
1. **工具调用支持具有高度的分化性**:
   各物理模型及服务商在 Function Calling 上的支持极度不均衡（例如，有些模型在 native SDK 下才支持工具；有些中转站不支持 `tool_choice`；有些模型在 `tools: true` 时仍存在高频的幻觉调用）。
2. **防止产生致命死循环 (Infinity Loop)**:
   普通聊天（`oct-chat`）为了追求极致响应速度和超低 Token 成本，可能会切换到极速/轻量模型。这些模型如果误入工具循环，极易因格式错误或参数拼写错误触发系统自愈逻辑，引发无限递归循环或大量调用报错。
3. **保证智能体（Agent）的任务成功率**:
   在 `agent_runner.js` 或 `toolLoop.js` 启动工具调用时，必须提供一条物理级别隔离、在平台层面经过 100% 格式验证、被声明为 `strict` 或 `loose` 级别的“安全通道”，即 `oct-tool-safe`。普通对话模型无论如何切换，工具调用的执行后端应当保持相对的高可靠与高刚性。
