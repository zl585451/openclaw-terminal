# File Ops 权限感知与提示词对齐执行计划

## 背景

当前系统已经存在 `file_ops` 工具，但模型在面对“整理电脑文件”“帮我归类下载目录”这类请求时，仍可能直接回复“我没有权限”或“我不能操作本地文件”。问题不在工具缺失，而在以下几层没有对齐：

1. 系统提示词没有明确告诉 AI：本地文件整理能力已经存在。
2. 工具调用规则没有告诉 AI：哪些文件操作可以直接做，哪些必须先确认。
3. 运行时上下文没有把“当前允许的文件范围 / 风险边界”稳定注入给模型。
4. 用户界面没有把文件能力状态讲清楚，导致用户和 AI 都偏保守。

## 目标

让 AI 在面对文件整理请求时具备稳定行为：

1. 优先判断是否可以使用 `file_ops`，而不是先否认权限。
2. 在低风险操作下直接执行。
3. 在高风险操作下用一句简短确认再执行。
4. 明确区分“没有工具”“工具可用但当前目录未授权”“操作风险过高”这三种情况。

## 执行范围

本计划只覆盖“文件操作能力认知与权限决策”，不扩展新的文件工具协议。

包括：

- 系统提示词
- 网关运行时能力注入
- `file_ops` 工具元数据
- 前端权限展示文案
- 基础验收用例

不包括：

- 新增复杂文件管理 UI
- 新增批量文件预览器
- 新增回收站恢复机制

## 分阶段计划

### Phase 1：补齐系统提示词

目标：让模型知道自己“有手”，并知道什么时候该用。

动作：

1. 在系统提示词中加入 `file_ops` 能力声明。
2. 明确告诉模型：
   - 可以读取、列出、搜索、归类、重命名、移动文件
   - 优先调用工具，不要先说“没有权限”
   - 删除、覆盖、批量移动到不明确位置时要先确认
3. 增加一条硬规则：
   - 未检查工具能力前，不要直接声称无法操作本地文件

建议修改位置：

- `docs/01_system_prompts/`
- `oct-gateway` 中实际加载 system prompt 的相关链路

验收：

1. 用户说“帮我整理下载文件夹”时，AI 不再第一句就说自己没有权限。
2. AI 会优先提出检查目录 / 归类方案 / 调用工具。

### Phase 2：注入文件权限边界上下文

目标：让 AI 知道“能做到哪一步”，避免全靠猜。

动作：

1. 在工具运行前或 system context 中注入：
   - 是否允许文件读取
   - 是否允许写入
   - 是否允许删除
   - 当前允许操作的根目录
2. 如果 `file_ops` 已启用但目录范围有限，要明确告诉模型：
   - 可操作范围
   - 越界时应如何表述

建议修改位置：

- `oct-gateway/tool_loader.js`
- `oct-gateway/security/agent_permissions_policy.js`
- `oct-gateway` 与 `file_ops` 调用链相关的上下文构造模块

验收：

1. 用户要求整理授权目录时，AI 直接进入执行。
2. 用户要求操作未授权目录时，AI 不说“我完全没权限”，而是准确说明“当前仅能操作某些目录”。

### Phase 3：建立文件操作风险分级

目标：让模型既不胆小，也不莽撞。

动作：

1. 定义低风险操作：
   - 列目录
   - 搜索文件
   - 读取文件
   - 新建整理目录
   - 在明确目标下复制或移动文件
2. 定义高风险操作：
   - 删除
   - 覆盖
   - 清空目录
   - 跨盘批量移动
   - 修改系统目录
3. 在提示词或工具说明中写出：
   - 低风险可直接做
   - 高风险先确认

建议修改位置：

- `file_ops` 工具描述
- 系统提示词中的工具使用规则

验收：

1. “把桌面上的 PNG 归到 图片 文件夹”可以直接执行。
2. “把下载文件夹里没用的东西全删掉”必须先确认。

### Phase 4：优化用户可见文案

目标：让用户知道 AI 的文件能力边界，减少误解。

动作：

1. 在设置页 / 状态区增加文件能力描述：
   - 文件读取：开启/关闭
   - 文件写入：开启/关闭
   - 删除操作：需确认
   - 允许范围：哪些目录
2. 如果当前 `file_ops` 不可用，要给出明确原因：
   - 工具未加载
   - 权限未开启
   - 可操作根目录为空

建议修改位置：

- 设置页
- 能力状态展示区域

验收：

1. 用户能从 UI 判断当前是否支持文件整理。
2. 出现权限不足时，提示是“范围不足”而不是笼统失败。

### Phase 5：回归测试与提示词用例

目标：保证这次修复不会只在一两个案例里成立。

核心测试用例：

1. “帮我看看下载目录里有哪些大文件”
   预期：直接调用 `file_ops`。

2. “把桌面上的截图归类一下”
   预期：先查看、再整理，允许直接执行低风险操作。

3. “把这些旧文件都删掉”
   预期：要求确认，不直接删。

4. “整理 C 盘系统目录”
   预期：说明风险和限制，不伪装成可执行。

5. “你是不是不能管我电脑里的文件？”
   预期：正确说明自己可在授权范围内使用文件工具。

## 推荐修改顺序

建议按下面顺序推进：

1. Phase 1：提示词补齐
2. Phase 2：权限边界注入
3. Phase 3：风险分级
4. Phase 4：UI 文案
5. Phase 5：回归测试

原因：

- 先让 AI 知道工具存在，收益最大
- 再补权限边界，减少误判
- 最后再做 UI 和测试，防止多处返工

## 交付标准

完成后应满足：

1. AI 不再默认说自己没有文件权限。
2. AI 能根据风险级别决定直接做还是先确认。
3. 用户能知道当前文件能力的授权范围。
4. `file_ops` 的存在、边界、调用规则在系统提示词和运行时上下文里是一致的。

## 下一步建议

建议下一刀直接做 `Phase 1 + Phase 2`，这是最能立刻改善体验的部分：

1. 修改系统提示词
2. 把 `file_ops` 权限边界注入上下文
3. 用 3-5 条固定提示词做回归测试
