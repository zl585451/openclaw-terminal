# 记忆系统（Nocturne Memory）掉线修复报告

**日期**: 2026-03-16  
**版本**: OCT v0.1.7 发布前  
**状态**: 已实施代码修复，待你本地验证

---

## 1. 问题诊断报告

### 1.1 现象

- Gateway 后端状态显示「不可用」
- 已加载记忆显示 **0 个 domain**
- 记忆系统频繁掉线，影响发布

### 1.2 排查结果摘要

| 检查项 | 结果 |
|--------|------|
| Gateway 进程 | 有（Node，端口 18789/18790 监听） |
| Nocturne 后端进程 | 有（Python PID 26672），但 **127.0.0.1:8000 连接被拒绝** |
| 端口占用 | 8000 被占用，但 **无法连通**（目标计算机积极拒绝） |
| 配置文件 | `config.js` 中 `NOCTURNE_BASE_URL=http://127.0.0.1:8000`，正确 |
| 健康检查 | Gateway 的 `memory.isAlive()` 请求 `GET /health`，仅当 `res.ok` 时为可用 |

### 1.3 根因结论

1. **Nocturne 后端未真正就绪或启动后崩溃**
   - 本机探测 `http://127.0.0.1:8000/` 与 `http://127.0.0.1:8000/health` 均返回「目标计算机积极拒绝」。
   - 可能原因：  
     - 后端由 Electron 在 `app.whenReady()` 时 spawn，但 **未注入 `DATABASE_URL`**，仅依赖 `nocturne_memory/.env`；若 `.env` 缺失或路径不对，`get_db_client()` 在 lifespan 里会抛错，导致 uvicorn 未完成绑定或进程退出。  
     - `.env` 只写在 **nocturne_memory 根目录**，而 uvicorn 的 cwd 是 **backend**，部分环境下 `find_dotenv(usecwd=True)` 可能未找到根目录 `.env`，从而 `DATABASE_URL` 未设置，初始化失败。

2. **健康检查依赖 DB**
   - Nocturne 的 `/health` 在 DB 未连接时返回 **503**（`status: degraded`, `database: disconnected`）。
   - Gateway 的 `isAlive()` 只看 `res.ok`，503 即视为不可用，UI 显示「不可用」和 0 个 domain。

3. **就绪判断仅看端口**
   - Electron 里 `startNocturneBackend()` 只等「端口 8000 被占用」，未等 **/health 返回 200**，因此可能认为已就绪，但此时 DB 未连上或进程即将退出，导致后续请求失败、表现「老掉线」。

## 2. 修复步骤记录

### 2.1 代码修改（已完成）

**文件: `electron/main.ts`**

1. **`ensureNocturneEnv()`**
   - 保证 `userData` 目录存在（`fs.mkdirSync`）。
   - 除 `nocturne_memory/.env` 外，**同时写入 `nocturne_memory/backend/.env`**，内容一致（含 `DATABASE_URL`），确保 uvicorn cwd=backend 时一定能加载到 `.env`。
   - 仍保留：若根目录 `.env` 已存在则跳过写入，避免覆盖用户自定义。

2. **`startNocturneBackend()`**
   - 在 spawn 时**显式传入环境变量**：  
     `DATABASE_URL=sqlite+aiosqlite:///<userData>/nocturne_memory.db`（与 `ensureNocturneEnv` 一致）。
   - 端口就绪后，**增加对 `/health` 的轮询**（最多约 20×0.5s）：只有收到 **HTTP 200** 才视为「后端 + DB 就绪」，并发送「记忆系统已启动」日志。
   - 若端口已监听但 `/health` 一直非 200，仍返回 `true`，并提示用户可点击「重启 Nocturne 后端」。

**未改动的相关逻辑**

- `oct-gateway/memory.js` 的 `isAlive()` 仍为「`res.ok` 即可用」，503 仍视为不可用（与后端语义一致）。
- Nocturne 的 `health.py` 未改：DB 断开仍返回 503。

### 2.2 配置与备份

- 未修改任何用户已有配置文件；仅在「根目录 `.env` 不存在」时自动生成/写入上述两个 `.env`。
- 无需单独备份：`.env` 为自动生成，且不会覆盖已存在的根目录 `.env`。

## 3. 验证测试建议

请你本地按下面步骤做一次完整验证（含约 10 分钟稳定测试）。

1. **重启 OCT 应用**
   - 完全退出后重新启动，让新代码生效（含 Nocturne 启动与健康检查逻辑）。

2. **检查 Gateway 状态**
   - 在界面中确认 Gateway 显示为「可用」（绿色/正常状态）。

3. **检查记忆系统状态**
   - 设置/记忆系统 Tab：  
     - 后端状态应为「可用」；  
     - **已加载记忆**应 **> 0 个 domain**（若从未初始化，可先执行「初始化预设记忆」或「重启 Nocturne 后端」后再看）。

4. **功能测试**
   - 在对话中发一条可触发记忆保存的消息（或使用「添加任务」等）；  
   - 关闭并重新打开 OCT（或刷新/重连），确认记忆或任务仍存在（跨会话保留）。

5. **稳定运行约 10 分钟**
   - 保持 OCT 与 Gateway、Nocturne 运行约 10 分钟，期间偶尔切换 Tab、发几条消息；  
   - 再次确认：Gateway 仍可用、已加载 domain 数未变回 0、无「掉线」现象。

若某一步不符合预期，请查看：
- **Electron 主进程控制台**（或打包后的日志）：是否有 `[Nocturne]` 相关报错或 stderr 输出。
- **右侧 Gateway 日志区**：是否有 `[Memory] ⚠️ Nocturne 离线` 等提示。

## 4. 预防建议（避免再次掉线）

1. **启动顺序与依赖**
   - 保持当前设计：OCT 启动时先 `ensureNocturneEnv()`，再 `startNocturneBackend()`，且 spawn 时**始终传入 `DATABASE_URL`**，不依赖工作目录下是否已有 `.env`。
   - 不要删除或随意修改 `userData` 下的 `nocturne_memory.db`；若需重置记忆，通过应用内「初始化」或备份后删除 DB 再重启。

2. **端口与进程**
   - 避免其他程序长期占用 **8000**；若需同时跑多个 Nocturne 实例，后续可考虑通过配置切换端口（当前为固定 8000）。
   - 若发现「不可用」但进程仍在：在设置里使用「**重启 Nocturne 后端**」先尝试恢复，再查日志。

3. **健康检查与日志**
   - 已通过「等 /health 200 再报就绪」减少「假就绪」；若仍出现掉线，可把 Nocturne 的 stderr 持久化到文件（例如写入 `userData` 下的日志），便于排查 DB 或依赖错误。

4. **发布前检查清单**
   - 在发布 v0.1.7 前，在目标环境（Windows 本机 + 打包后）各做一次：冷启动 → 检查 Gateway 与记忆状态 → 做一次记忆读写 + 跨会话保留 → 稳定跑 10 分钟，确认无掉线再发版。
