## 3. 根因分析

### 3.1 可能原因（按优先级）

| 优先级 | 原因 | 说明 |
|--------|------|------|
| 1 | **SQLite 并发锁竞争** | 未设 `busy_timeout`，多路并发写入时易出现 SQLITE_BUSY，请求快速失败 |
| 2 | **self_eval 连续写入放大** | 每回复 1 次评估写入 + 每 20 条 1 次模式提炼，触发大量递归读/写 |
| 3 | **6 路并发请求** | 单条回复触发 6 个并行 Nocturne 调用，易打满连接、堆积锁 |
| 4 | **Nocturne 单进程瓶颈** | uvicorn 单 worker，请求串行处理，堆积时响应变慢直至超时 |
| 5 | **DB 锁未及时释放** | 长事务或异常路径可能导致连接/锁未释放，加剧锁竞争 |

### 3.2 掉线时间线（推断）

1. 17:09 前：对话密集，self_eval 频繁写入 + 可能触发 `maybeDistill`
2. Nocturne 端：SQLite 锁竞争，请求排队或失败
3. Gateway：多次 8 秒超时 → `memory.isAlive()` 失败 → 判定 Nocturne 离线
4. 17:09:58：Nocturne 进程重启（崩溃或手动重启）

## 4. 建议方案

### 4.1 短期（必做）

1. **SQLite 增加 busy_timeout**（`sqlite_client.py`）  
   在 `set_sqlite_pragma` 中增加：

   ```python
   cursor.execute("PRAGMA busy_timeout=10000")  # 10 秒
   cursor.execute("PRAGMA journal_mode=WAL")    # 提升并发
   ```

2. **self_eval 写入限流 / 串行化**  
   - 对 `evaluateReply` 和 `maybeDistill` 做简单队列或限流  
   - 避免同一时刻多条评估 + 模式提炼同时压入 Nocturne

3. **增加 Nocturne 日志持久化**  
   - 将 stderr 写入 `userData/nocturne_stderr.log`  
   - 便于后续排查 DB 错误和锁问题

### 4.2 中期

4. **Gateway 写入错峰**  
   - 将 6 路 Nocturne 调用改为队列或错峰执行  
   - 减少同时发往 Nocturne 的并发请求数

5. **self_eval 模式提炼异步化**  
   - `maybeDistill` 改为后台任务，不阻塞 `evaluateReply`  
   - 提炼失败时只记录，不重试阻塞主流程

6. **memory.js 超时区分**  
   - 健康检查 1.5 秒可保持  
   - 普通请求 8 秒可接受，必要时对重操作（如模式提炼）单独加长

### 4.3 长期

7. **任务看板已独立**（`docs/feature-map`）  
   - 任务已迁移到 `userData/tasks.json`，减轻 Nocturne 负载

8. **self_eval 写入可选降级**  
   - 配置开关：高负载时可暂时关闭或降低评估频率

9. **监控与告警**  
   - 记录 Nocturne 请求失败率、超时次数  
   - 失败率超阈值时在 UI 或日志中提醒
